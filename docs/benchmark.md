# 하네스 품질 벤치마크

**같은 작업을 현재 하네스를 쓰고 안 쓰고 각각 실행해 결과물을 비교합니다.**
하네스의 완료 선언이나 실행한 도구 수에는 점수를 주지 않습니다. 실제 기능 검사와
결과물 평가를 통과해야 하며, 특정 과제의 악화를 전체 평균으로 숨기지 않습니다.
하네스를 수정하면 같은 설정의 직전 통과 결과와 **수정 전후**도 자동 비교합니다.

## 비교 대상과 판정

| 대상 | 실행 조건 | 확인할 질문 |
| --- | --- | --- |
| `plain` | 프로젝트 지침만 있는 새 작업 공간 | 하네스 없이 얻는 결과는 무엇인가? |
| `candidate` | 현재 파일의 하네스 설치·스킬 시작 | 하네스를 사용하면 실제 결과가 좋아지는가? |

두 조건은 같은 초기 파일·요청·루트 대화의 모델·effort·호출 한도·시간 한도를 사용합니다.
기본은 하위 호출도 고정하고, 라우팅 평가에서는 같은 허용 모델·effort 풀을 제공합니다.
각 실행은 새 Git 저장소, 공급자 대화, 지식베이스를 갖습니다. 한 과제의 후속 입력은
같은 실제 Claude/Codex 대화를 재개합니다. 폴더가 바뀌어도 세션은 유지합니다.
과제·반복·대상 순서를 고정 시드로 섞어 실행 순서 영향을 줄입니다.

| 평가 | 근거 | 기본 차단 조건 |
| --- | --- | --- |
| 기능·사실 정확성 | 에이전트 작업 종료 후 별도 복사본에서 실행하는 검사 | 필수 검사 실패 |
| 완성도·사용성·설명 | 조건별 0~4점 기준, 익명 결과물의 독립 평가 2회 | 총점 85 미만 또는 대조군보다 낮음 |
| 사용자 개입 | 요청·응답에서 추가 질문/절차 요구를 세고 근거 인용 | 대조군보다 증가 |
| 실행 시간 | 하위 작업을 포함한 과제 전체 경과 시간 | 대조군의 3배 + 10초 초과 |
| 호출·사용량 | 하위 CLI까지 허용 프로필과 공통 호출 장부 적용 | 공통 호출/시간 예산 소진 시 미완료 |

가중치·임계값은 `benchmarks/suite.json`에 있으며 **비교 전에 고정**합니다.
기본 점수는 실제 검사 70%, 사용성 15%, 자율 수행 15%입니다. 평가자 간 점수가
다르면 낮은 점수를 사용하고 불일치를 기록합니다. 점수가 좋을 때까지 재평가하지 않습니다.
시간과 사용자 개입은 품질 점수와 별도 게이트입니다.

| 판정 | 의미 | 게이트 종료 코드 |
| --- | --- | --- |
| `improved` | 회귀 없음; 첫 실행은 미사용 대비, 이전 기준이 있으면 전후 품질·하네스 효과 변화의 구간 하한이 모두 양수 | 0 |
| `non_regressing` | 정한 기준에서 회귀 없음; 개선을 입증한 것은 아님 | 0 |
| `regression` | 필수 결과·품질·개입·시간 중 하나라도 기준 위반 | 1 |
| `inconclusive` | 반복·평가·비교 대상·유효한 실행 등 근거 부족 | 3 |

잘못된 입력·변경된 증거는 종료 코드 2로 거절합니다. 실행 실패한 대조군은 개선의
증거가 아닙니다. 실제 모델을 쓰지 않은 시뮬레이션은 품질 게이트를 통과할 수 없습니다.
짝지은 점수 차이의 bootstrap 95% 구간은 해당 과제의 기술 통계이며, 적은 공개 과제로
다른 프로젝트나 모델에서도 더 좋다고 일반화할 수 없습니다.

## 터미널에서 실행

벤치마크는 독립 CLI입니다. 대화 세션을 직접 열거나 스킬을 미리 활성화하지 않아도 됩니다.
스크립트가 로그인된 Claude/Codex CLI의 실행과 평가용 세션을 관리합니다. 기준 커밋을
선택하지 않고 현재 하네스 파일을 복사해 사용/미사용 두 조건만 실행합니다.

모델 변수는 해당 계정에서 사용 가능한 구체적인 모델 ID, effort 변수는 그 모델과 CLI가
지원하는 명시적 수준으로 설정합니다. 결과 디렉터리는 소스·과제 디렉터리 밖의 새 경로여야 합니다.
대화로 벤치를 요청하면 에이전트가 같은 CLI를 실행합니다. 상시 실행 훅은 없습니다.

### 한 번에 실행

```sh
python3 scripts/benchmark.py \
  --claude-model "$BENCH_CLAUDE_MODEL" --claude-effort "$BENCH_CLAUDE_EFFORT" \
  --codex-model "$BENCH_CODEX_MODEL" --codex-effort "$BENCH_CODEX_EFFORT" \
  --output "$BENCH_RUN_DIR"
```

`python3 scripts/loop.py bench check`도 같은 명령입니다. 비교 실행 → 외부 검사 → 독립 평가 →
현재 소스 게이트 → 개선 리포트를 순서대로 수행합니다. 실행 직후의 미채점 상태 때문에
다음 단계가 생략되지 않습니다. 모델·effort 네 인수가 필수이고 나머지 기본값은 다음과 같습니다.

| 설정 | 기본값 / 변경 방법 |
| --- | --- |
| 목표 유형 | 개발·문서·설명, 과제 6개; `--suite`로 변경 |
| 실행 제공자 | Claude와 Codex 모두; `--provider`로 선택 |
| 평가할 하네스 | 스크립트가 속한 현재 소스 디렉터리; `--candidate`로 변경 |
| 반복 / 순서 | 3회 / 시드 0; `--repeats`, `--seed` |
| 공통 평가자 | 지정한 Codex 모델·effort, 독립 평가 2회 |
| 평가자 변경 | `--judge-provider`, `--judge-model`, `--judge-effort`, `--judge-repeats` |
| 결과 경로 | 소스 옆 `loop-dev-benchmarks/<시각>-<실행 ID>/`; `--output` |
| 전후 비교 기록 | 소스 옆 `loop-dev-benchmarks/history/<소스 경로 ID>/`; `--history` |
| 환경 기록 | 현재 OS·아키텍처와 CLI 프로필 해시; `--environment`로 설명 지정 |
| 작업별 모델 선택 평가 | 기본은 고정 설정; `--routing-profile FILE`로 공통 허용 풀 지정 |

커밋되지 않은 수정도 현재 파일 그대로 평가합니다. 소스·과제·결과의 해시는 자동 기록하며,
평가 후 파일이 바뀌면 기존 통과 결과를 현재 변경의 근거로 사용할 수 없습니다.
실행 전에 `--dry-run`으로 목표 유형, 두 실행 조건, 설정, 평가자와 호출/시간 상한을
확인할 수 있습니다. 이 옵션은 모델 호출이나 결과 디렉터리 생성을 하지 않습니다.

평가자 제공자·모델·effort·반복 수는 실행 manifest에 먼저 고정합니다. 모든 실행 제공자와
비교군을 같은 평가자로 채점하며, 점수를 본 뒤 설정을 바꿀 수 없습니다. 평가 실패나
게이트 오류도 `check.json`과 개선 리포트에 남기고 `inconclusive`(코드 3)로 끝냅니다.
입력 자체가 잘못되었으면 실행 전에 코드 2로 거절합니다.

### 하네스를 수정할 때

1. **수정 전:** 현재 소스와 설정의 통과 기록이 없으면 위 명령을 한 번 실행합니다.
   최초 통과 결과가 자동 기준이 됩니다. 기록이 이미 있으면 재사용합니다.
2. **수정 후:** 같은 모델·effort·과제·설정으로 같은 명령을 실행합니다.
   `--output`을 지정했다면 새 디렉터리를 사용합니다.
3. **판정:** 현재 사용/미사용 비교와 직전 통과 버전 대비를 모두 확인합니다.
   둘 다 통과한 변경만 다음 비교 기준으로 저장합니다.

하네스 개발을 요청한 경우 이 절차는 에이전트가 수행합니다. 사용자가 기준 커밋이나 이전
결과 경로를 매번 선택하지 않습니다. 최초 기준 없이 이미 수정했다면 그 실행은 새 기준
수집이며, 측정하지 않은 수정 전 결과를 추정하지 않습니다.

전후 비교는 이전 실행의 검증된 원본 근거를 재사용합니다. 각 새 실행은 여전히 사용/미사용
두 조건만 수행하므로 과제 실행 수가 세 조건으로 늘지 않습니다. **기록과 이전 결과 디렉터리를
함께 보관**해야 합니다. 이전 결과가 사라지거나 바뀌면 기준을 덮어쓰지 않고 근거 부족으로 끝납니다.

| 전후 판정 | 기준 처리 |
| --- | --- |
| `baseline_created` | 이전 근거가 없는 설정의 첫 기준; 전후 개선 주장은 불가 |
| `improved` | 각 평가 항목에서 퇴행 없이 품질과 하네스 효과가 함께 증가; 기준 갱신 |
| `non_regressing` | 정한 기준에서 퇴행 없음; 변경된 소스라면 기준 갱신, 개선 주장은 불가 |
| `regression` / `inconclusive` | 기존 기준 유지; 실패한 실행도 결과 디렉터리에 보존 |

전후의 각 과제·제공자·반복을 짝지어 **평가 항목별 점수 감소**, 추가 질문 증가,
동일한 시간 한도 위반을 확인합니다. 한 항목의 손실을 다른 항목이나 목표 유형의 이득으로
상쇄하지 않습니다. 시간 한도는 이전 실행 시간 × 설정 배수 + 허용 초로 계산합니다.
호출 수와 사용량은 별도로 기록합니다.

리포트의 **하네스 효과 변화 = 사용 점수 변화 − 미사용 점수 변화**입니다. 전후 개선 판정에는
사용 점수 변화와 하네스 효과 변화의 bootstrap 구간 하한이 모두 양수여야 합니다.
미사용 결과만 나빠졌거나 양쪽이 같이 좋아진 경우를 하네스 개선이라고 표시하지 않습니다.
같은 소스의 반복 측정은 기준을 교체하지 않아 유리한 결과만 골라 기준을 높이지 않습니다.

과제·검사·평가 기준, 두 제공자의 모델·effort, 라우팅 모드·허용 풀, 평가자·평가 횟수, 제공자 선택, 반복 수,
시드, 예산, 환경·설정 해시, CLI 버전이 같아야 전후 비교합니다. 바뀐 설정은 별도 기준으로
기록하며 기존 기록을 지우지 않습니다. 모델 비교와 하네스 변경 비교를 섞지 마세요.
같은 모델 ID의 서비스 내부 변경이나 시간대 차이는 완전히 통제할 수 없습니다.

동시에 실행한 다른 작업이 기준을 먼저 바꾸면 현재 실행은 근거 부족으로 남깁니다.
전후 결과는 `improvements.md`와 `report.json`에 포함되며, 나중에 `bench gate`를 실행해도
동일한 전후 근거를 다시 확인합니다. 기록 삭제나 기준 완화로 회귀를 우회하지 않습니다.

### 설정의 적용 범위

| 모드 | 루트 대화 | 하위 작업·검토·재시도 |
| --- | --- | --- |
| 기본 고정 모드 | CLI 인수의 모델·effort | 같은 공급자별 설정만 허용 |
| `--routing-profile FILE` | CLI 인수의 모델·effort 유지 | 두 조건에 제공한 같은 풀 안에서 명시적으로 선택 |

라우팅 파일은 [라우팅 규칙](../rules/routing.md)의 정책 JSON입니다. CLI에 지정한 Claude와
Codex 모델·effort 조합을 **둘 다** 포함해야 합니다. `plan`, `run`, `check`에서 같은 옵션을
사용합니다. 평가자는 별도 고정 설정으로 실행하며 작업자 풀에서 선택하지 않습니다.

```sh
python3 scripts/benchmark.py \
  --claude-model "$BENCH_CLAUDE_MODEL" --claude-effort "$BENCH_CLAUDE_EFFORT" \
  --codex-model "$BENCH_CODEX_MODEL" --codex-effort "$BENCH_CODEX_EFFORT" \
  --routing-profile /absolute/routing-policy.json
```

허용 풀은 두 조건에 `LOOP_ROUTING_PROFILE`로 제공하며 목표 고정 전에 가져옵니다.
풀 밖의 모델·effort나 서로 충돌하는 설정은 거절합니다. 옵션을 생략하면 공급자별 고정 조합
하나씩만 있는 정책을 생성하므로 더 높은 재시도 프로필을 임의로 추가하지 않습니다.
고정 모드에서 라우팅 모드로 바꾸거나 풀을 바꾸면 별도 전후 기준을 만듭니다.
다른 설정의 결과를 이전 하네스보다 개선된 근거로 사용하지 않습니다.
라우팅 정보가 없는 과거 실행과 새 고정/라우팅 정책 실행도 비교 설정이 다릅니다. 업그레이드
후 첫 통과는 새 기준이며 전후 개선이 아닙니다. 과거 리포트는 당시 근거로 재검증할 수 있고,
이후 같은 정책의 실행끼리는 정상적으로 전후 비교합니다.

모든 하위 작업·검토·재시도·실패 호출은 같은 호출·시간 예산을 사용합니다. 리포트는 실제
요청한 조합별 호출·실패·미완료를 보존하며, 폐기·재시도·상향 여부는 연결된 실행·평가 근거가
있을 때만 표시합니다. 근거가 없으면 추정하지 않습니다. 모델을 많이 쓰거나 큰 모델을
선택했다는 사실 자체에 점수를 주지 않습니다.

지원하지 않는 설정은 CLI 오류로 남기고 다른 수준으로 대체하지 않습니다.
`auto`/`default`는 허용하지 않습니다. 전역 설정 파일은 수정하지 않습니다.

Codex에는 `model_reasoning_effort`와 `plan_mode_reasoning_effort`를 같은 값으로 넘깁니다.
Claude에는 `--effort`와 해당 호출의 `CLAUDE_CODE_EFFORT_LEVEL`을 같은 값으로 넘깁니다.
Claude의 호출별 fallback도 선택 모델로 제한하고 전환 질문을 끄며, 다른 모델·체인 요청은
거절합니다. 기존 호스트 파일과 관리 정책은 보존합니다.
지원 수준은 모델과 클라이언트에 따라 다릅니다. [Codex 설정 참조](https://developers.openai.com/codex/config-reference/)와
[Claude CLI 참조](https://code.claude.com/docs/en/cli-reference)를 확인하세요.
기록한 설정은 요청값입니다. 관리 정책이 effort를 낮출 수 있으므로 실제 적용 수준을 관측하지
않았다면 그대로 실행됐다고 단정하지 않습니다. 같은 effort 이름이나 정책의 비용 순위는
공급자 사이의 같은 연산량·가격을 뜻하지 않으며, 알 수 없는 실제 청구액은 채우지 않습니다.

### 단계별 실행

수동 분석이 필요할 때 사용하는 하위 명령입니다. `plan`은 모델을 호출하지 않습니다.

```sh
python3 scripts/loop.py bench plan \
  --suite benchmarks/suite.json --candidate . \
  --codex-model "$BENCH_CODEX_MODEL" --claude-model "$BENCH_CLAUDE_MODEL" \
  --codex-effort "$BENCH_CODEX_EFFORT" --claude-effort "$BENCH_CLAUDE_EFFORT" \
  --provider codex --provider claude --repeats 3 --seed 17 \
  --environment "dedicated benchmark profile; fixed host and provider settings"

python3 scripts/loop.py bench run \
  --suite benchmarks/suite.json --candidate . \
  --codex-model "$BENCH_CODEX_MODEL" --claude-model "$BENCH_CLAUDE_MODEL" \
  --codex-effort "$BENCH_CODEX_EFFORT" --claude-effort "$BENCH_CLAUDE_EFFORT" \
  --provider codex --provider claude --repeats 3 --seed 17 \
  --environment "dedicated benchmark profile; fixed host and provider settings" \
  --output "$BENCH_RUN_DIR"

python3 scripts/loop.py bench judge "$BENCH_RUN_DIR" \
  --provider codex --model "$BENCH_JUDGE_MODEL" --effort "$BENCH_JUDGE_EFFORT" --repeats 2

python3 scripts/loop.py bench gate "$BENCH_RUN_DIR" \
  --candidate . --suite benchmarks/suite.json
```

기본 과제 6개 × 대화 공급자 2개 × 반복 3회 × 사용/미사용 2조건 = **72회 과제 실행**입니다.
별도 결과물 평가는 기본 144회입니다. `plan`에 호출 수 상한과 과제 시간 상한을 표시합니다.
과제당 기본 한도는 하위 작업을 포함해 CLI 60회·20분입니다. 모델 비용과 내부 추론량은
공급자마다 다르므로 같은 모델과 상한을 맞춰도 정확히 같은 지출을 보장하지 않습니다.
전송·구성 확인은 `--repeats 1`로 가능하지만 품질 통과 근거로 사용할 수 없습니다.

실행 중에는 stderr와 `index.json`에서 완료 수를 확인합니다. `run` 직후에는 결과물
평가가 없으므로 보통 코드 3을 반환합니다. 이것은 `judge` 전의 정상적인 근거 부족 상태입니다.
셸의 `&&`로 `run`과 `judge`를 연결하면 평가가 생략될 수 있으므로 전체 실행에는 `bench check`를 사용합니다.
실패·부분 실행의 로그를 보존하며, 재실행은 새 디렉터리에 모든 대상을 실행합니다.

두 CLI에 기존 인증이 필요합니다. 하네스의 교차 검토까지 비교하므로 `--provider`를
하나만 선택해도 두 CLI가 필요합니다. 별도 API 키나 SDK는 필요하지 않습니다.
중첩 실행·쓰기 권한을 호스트가 거절하면 제한을 우회하지 않고 근거 부족으로 보고합니다.

## 결과와 규칙 개선

| 경로 | 용도 |
| --- | --- |
| `check.json` | 전체 실행의 단계·최종 판정·오류·선택 설정 |
| `evolution.json` | 자동 선택한 수정 전 실행, 원본 근거 해시, 비교 설정 식별자 |
| `improvements.md` | 설정별 비교, 유형별 완료/판정, 우선순위 상위 5개 개선 항목 |
| `improvements.json` | 전체 유형별 측정값, 묶인 개선 항목, 관측·가설·관련 규칙·다음 변경·재검증 |
| `report.md` | 판정, 과제별 차이, 근거 부족, 조사할 규칙 |
| `report.json` | 평가 항목별 점수·근거·불일치·개입·시간·사용량 |
| `manifest.json`, `index.json` | 모델/effort·라우팅 모드/정책·평가자/CLI 버전·환경·소스/과제 해시·실행 완전성 |
| `trials/<id>/packet.json` | 대상·모델·하네스 상태를 제외한 평가 입력 |
| `trials/<id>/` | 작업 결과, 요청/응답, 프로세스·검사·호출 로그 |
| `judgments.json`, `judges/` | 동일 평가 모델의 반복 평가와 원본 로그 |
| `proposals/` | 관찰된 결과와 연결한 규칙 변경 가설 |

개선 리포트는 측정 데이터에서 생성하므로 추가 모델 호출이 없습니다. 같은 사례·제공자·평가
항목의 반복 실패를 하나로 묶고, 실행/근거 문제(P0), 품질/추가 질문(P1), 시간/평가 불일치(P2)
순으로 표시합니다. **관측된 문제와 원인 가설을 분리**하며 조사할 규칙 경로를 확정 원인으로
표현하지 않습니다. 회귀가 없으면 불필요한 규칙 변경을 만들어내지 않습니다.
미측정 품질·시간·사용량은 0으로 채우지 않습니다. 전체 평균과 별개로 유형별 결과와 개별
사례의 회귀를 확인합니다. 전체 실행이 중단되면 기존 중간 report가 있어도 통과 근거로 사용하지 않습니다.

1. 실패한 과제와 평가 항목의 **실제 결과물·근거**를 읽습니다. 관련 규칙 경로는 원인
   후보이며, 인과관계를 증명한 것은 아닙니다.
2. 원인을 좁혀 `hypothesis`, `rule_paths`, `case_ids`, `expected_change`를 가진 짧은
   JSON을 작성하고 `bench proposal RUN --input FILE`로 저장합니다. 해당 과제 점수와
   회귀 근거, 소스·평가 기준 해시가 함께 고정됩니다.
3. 범위가 분명한 변경을 구현합니다. 점수를 올리기 위해 검사·가중치·완료 기준을 완화하거나
   과제의 정답을 일반 규칙에 넣지 않습니다.
4. 같은 모델·effort·라우팅 정책·과제로 새 디렉터리에서 하네스 사용/미사용 두 조건을 다시 실행합니다.
   `bench check`가 직전 통과 결과와 전후도 비교합니다. 조정용 과제와 재검증용 과제를
   모두 통과해야 하며 실패한 결과가 기존 기준을 대체하지 않습니다.
5. 현재 코드에 대해 `bench gate`를 실행합니다. 코드·규칙·스킬·평가 기준·검사·초기 파일이
   측정 후 바뀌면 이전 결과를 재사용할 수 없습니다. 병합·배포는 별도의 허용 범위를 따릅니다.

품질 게이트를 확인한 릴리스/승격 절차에서 `bench gate`의 종료 코드를 사용합니다.
기본 CI는 단위·시뮬레이션 테스트만 실행합니다. 모델 인증·비용을 요구하는 실측은 자동 CI에
숨겨 넣지 않으며, 단위 테스트 성공을 실제 품질 검증 완료로 표시하지 않습니다.

## 과제와 평가 확장

**서로 다른 목표 유형이 최소 2개** 있어야 실행됩니다. 개발 사례 여러 개만으로는 충분하지
않습니다. 기본 구성은 `development`, `document`, `explanation`이며 `research`, `review`,
`planning`도 지원합니다. 기존 `session` 사례는 설명 목표의 세션 재사용 시나리오이므로
`explanation`에 합산합니다. 세션을 바꾸거나 같은 목표를 반복한 것을 새 목표 유형으로 세지 않습니다.
유효한 결과를 위해 모든 유형을 선택한 제공자·두 실행 조건·반복에서 완료하고 채점해야 합니다.

기본 과제는 저장/재조회, 입력 오류와 데이터 보존, 소스 설명, 실행 가능한 문서 예제,
작은 수정, 폴더 이동과 지식 최신화를 다룹니다. `calibration`은 원인 분석에,
`holdout`은 변경의 다른 영향 확인에 씁니다. 둘 다 공개된 예제이므로 진정한 비공개
검증 세트를 대신하지 않습니다. 실제 작업의 대표 과제와 별도 보관한 과제를 추가하세요.

각 과제는 초기 파일 경로, 작업 폴더, 순차 요청, 선언한 결과물, 변경 금지 파일,
외부 Python 검사, 가중 평가 항목을 갖습니다. `before`는 후속 요청 전 외부 변경을
재현합니다. `context`는 평가자가 사실 확인에 사용할 초기 소스 경로이며, 해당 소스와
후속 외부 변경도 평가 입력에 넣습니다. 검사 프로그램은 작업 디렉터리·응답 JSON·과제 ID를 인수로 받아 다음
형태로 모든 `check` 항목을 정확히 한 번 출력합니다.

```json
{"criterion_id": {"passed": true, "evidence": "관찰한 동작과 기대 결과"}}
```

평가자는 `packet.json`의 요청·응답·선언 소스·전체 선언 결과물만 받습니다. 각 `rubric`에는
0~4점의 구체적인 기준 다섯 개가 필요합니다. 함수 정확성만 자동 검사하는 과제도
추가 사용자 요구의 유무는 평가합니다. 사람의 평가 JSON도 `report/gate --judgments FILE`로
입력할 수 있습니다. 별도 `bench run`으로 시작한 실행에는 `manifest_hash`, 고정 평가자 `{provider, model}` 식별자,
`repeats` 2~5, 표본별 `packet_hash`와 `reviews`가 필요합니다. 각 review는
`ratings: [{id, score, evidence}]`, `extra_user_requests`, `intervention_evidence`를 갖습니다.
`bench check`로 평가자를 고정한 실행은 `{provider, model, effort}`와 반복 수가 manifest와
정확히 일치해야 합니다. 사람이나 다른 모델의 사후 평가로 바꾸려면 별도 실험으로 기록합니다.

평가 코드는 에이전트에게 전달하지 않고 종료 후 별도 복사본에서 실행합니다. 다만 이는
**협력적인 로컬 평가**이며, 악의적인 코드에 대한 OS 격리나 완벽한 익명화는 아닙니다.
답변 문체로 대상을 추측할 수 있고, 글로벌 지침·훅·모델 자체의 변동도 남습니다. 하네스를
자동 실행하는 전역 설정이 없는 전용 프로필을 사용하고, 실험 조건을 고정하세요.
자격 증명과 전역 설정은 수정하지 않습니다. 지식베이스와 작업 파일만 실행마다 분리합니다.

Codex의 보고 토큰과 Claude의 세션 누적 비용 추정치를 보존합니다. 재개한 Claude 비용을
중복 합산하지 않으며, 알 수 없는 값은 `null`입니다. 공급자 내부 작업의 완전한 사용량이나
두 공급자를 합친 실제 청구액을 추정해 채우지 않습니다. 실행 한도는 관리하는 CLI 호출에
적용하며, 독립 프로세스를 고의로 남기는 코드까지 격리하는 장치는 아닙니다.
