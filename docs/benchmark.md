# 하네스 품질 벤치마크

**같은 요청의 결과물을 하네스 없음·기존 버전·변경 버전으로 비교합니다.**
하네스의 완료 선언이나 실행한 도구 수에는 점수를 주지 않습니다. 실제 기능 검사와
결과물 평가를 통과해야 하며, 특정 과제의 악화를 전체 평균으로 숨기지 않습니다.

## 비교 대상과 판정

| 대상 | 실행 조건 | 확인할 질문 |
| --- | --- | --- |
| `plain` | 프로젝트 지침만 있는 새 작업 공간 | 하네스 없이도 더 잘 끝내는가? |
| `reference` | 지정한 Git 커밋의 하네스 설치·스킬 시작 | 기존 하네스보다 나빠졌는가? |
| `candidate` | 현재 작업 트리의 하네스 설치·스킬 시작 | 변경으로 실제 결과가 좋아졌는가? |

세 대상은 같은 초기 파일·요청·공급자별 모델·호출 한도·시간 한도를 사용합니다.
각 실행은 새 Git 저장소, 공급자 대화, 지식베이스를 갖습니다. 한 과제의 후속 입력은
같은 실제 Claude/Codex 대화를 재개합니다. 폴더가 바뀌어도 세션은 유지합니다.
과제·반복·대상 순서를 고정 시드로 섞어 실행 순서 영향을 줄입니다.

| 평가 | 근거 | 기본 차단 조건 |
| --- | --- | --- |
| 기능·사실 정확성 | 에이전트 작업 종료 후 별도 복사본에서 실행하는 검사 | 필수 검사 실패 |
| 완성도·사용성·설명 | 조건별 0~4점 기준, 익명 결과물의 독립 평가 2회 | 총점 85 미만 또는 대조군보다 낮음 |
| 사용자 개입 | 요청·응답에서 추가 질문/절차 요구를 세고 근거 인용 | 대조군보다 증가 |
| 실행 시간 | 하위 작업을 포함한 과제 전체 경과 시간 | 대조군의 3배 + 10초 초과 |
| 호출·사용량 | 하위 CLI까지 고정 모델과 공통 호출 장부 적용 | 공통 호출/시간 예산 소진 시 미완료 |

가중치·임계값은 `benchmarks/suite.json`에 있으며 **비교 전에 고정**합니다.
기본 점수는 실제 검사 70%, 사용성 15%, 자율 수행 15%입니다. 평가자 간 점수가
다르면 낮은 점수를 사용하고 불일치를 기록합니다. 점수가 좋을 때까지 재평가하지 않습니다.
시간과 사용자 개입은 품질 점수와 별도 게이트입니다.

| 판정 | 의미 | 게이트 종료 코드 |
| --- | --- | --- |
| `improved` | 회귀가 없고, 하네스 없음 대비 점수 차이의 구간 하한이 양수 | 0 |
| `non_regressing` | 정한 기준에서 회귀 없음; 개선을 입증한 것은 아님 | 0 |
| `regression` | 필수 결과·품질·개입·시간 중 하나라도 기준 위반 | 1 |
| `inconclusive` | 반복·평가·비교 대상·유효한 실행 등 근거 부족 | 3 |

잘못된 입력·변경된 증거는 종료 코드 2로 거절합니다. 실행 실패한 대조군은 개선의
증거가 아닙니다. 실제 모델을 쓰지 않은 시뮬레이션은 품질 게이트를 통과할 수 없습니다.
짝지은 점수 차이의 bootstrap 95% 구간은 해당 과제의 기술 통계이며, 적은 공개 과제로
다른 프로젝트나 모델에서도 더 좋다고 일반화할 수 없습니다.

## 요청과 내부 실행

활성화된 대화에서는 다음처럼 요청합니다.

> 이번 규칙 변경이 하네스 없이 할 때와 기존 버전보다 나빠지지 않았는지 벤치로 확인해 줘.
> 악화된 과제는 원인을 찾아 규칙을 수정하고 같은 기준으로 다시 확인해 줘.

대화 에이전트가 비교 기준 커밋, 기존 모델 설정, 과제와 실행 예산을 확인하고 명령을
관리합니다. 이미 정한 조건은 다시 묻지 않습니다. 검증되지 않은 모델 이름이나 권한을
추측하지 않으며, 사용자가 정해야 할 미해결 조건만 시작 전에 구체화합니다.
벤치는 상시 실행 훅이 아닙니다. 하네스 변경 검증이나 명시적인 평가 요청에 사용합니다.

다음은 에이전트가 실행하는 내부 명령 예시입니다. 모델 변수는 해당 계정에서 사용 가능한
구체적인 모델 ID, 기준 변수는 변경 전 검증 대상 커밋 SHA로 설정합니다. 결과 디렉터리는
소스·과제 디렉터리 밖의 새 경로여야 합니다. `plan`은 모델을 호출하지 않습니다.

```sh
python3 scripts/loop.py bench plan \
  --suite benchmarks/suite.json --candidate . --reference-ref "$BENCH_REFERENCE_SHA" \
  --codex-model "$BENCH_CODEX_MODEL" --claude-model "$BENCH_CLAUDE_MODEL" \
  --provider codex --provider claude --repeats 3 --seed 17 \
  --environment "dedicated benchmark profile; fixed host and provider settings"

python3 scripts/loop.py bench run \
  --suite benchmarks/suite.json --candidate . --reference-ref "$BENCH_REFERENCE_SHA" \
  --codex-model "$BENCH_CODEX_MODEL" --claude-model "$BENCH_CLAUDE_MODEL" \
  --provider codex --provider claude --repeats 3 --seed 17 \
  --environment "dedicated benchmark profile; fixed host and provider settings" \
  --output "$BENCH_RUN_DIR"

python3 scripts/loop.py bench judge "$BENCH_RUN_DIR" \
  --provider codex --model "$BENCH_JUDGE_MODEL" --repeats 2

python3 scripts/loop.py bench gate "$BENCH_RUN_DIR" \
  --candidate . --suite benchmarks/suite.json
```

기본 과제 6개 × 대화 공급자 2개 × 반복 3회 × 대상 3개 = **108회 과제 실행**입니다.
별도 결과물 평가는 기본 216회입니다. `plan`에 호출 수 상한과 과제 시간 상한을 표시합니다.
과제당 기본 한도는 하위 작업을 포함해 CLI 60회·20분입니다. 모델 비용과 내부 추론량은
공급자마다 다르므로 같은 모델과 상한을 맞춰도 정확히 같은 지출을 보장하지 않습니다.
전송·구성 확인은 `--repeats 1`로 가능하지만 품질 통과 근거로 사용할 수 없습니다.

실행 중에는 stderr와 `index.json`에서 완료 수를 확인합니다. `run` 직후에는 결과물
평가가 없으므로 보통 코드 3을 반환합니다. 이것은 `judge` 전의 정상적인 근거 부족 상태입니다.
셸의 `&&`로 `run`과 `judge`를 연결하면 평가가 생략될 수 있으므로 각각 실행합니다.
실패·부분 실행의 로그를 보존하며, 재실행은 새 디렉터리에 모든 대상을 실행합니다.

두 CLI에 기존 인증이 필요합니다. 하네스의 교차 검토까지 비교하므로 `--provider`를
하나만 선택해도 두 CLI가 필요합니다. 별도 API 키나 SDK는 필요하지 않습니다.
중첩 실행·쓰기 권한을 호스트가 거절하면 제한을 우회하지 않고 근거 부족으로 보고합니다.

## 결과와 규칙 개선

| 경로 | 용도 |
| --- | --- |
| `report.md` | 판정, 과제별 차이, 근거 부족, 조사할 규칙 |
| `report.json` | 평가 항목별 점수·근거·불일치·개입·시간·사용량 |
| `manifest.json`, `index.json` | 모델/CLI 버전·환경·소스/과제 해시·실행 완전성 |
| `trials/<id>/packet.json` | 대상·모델·하네스 상태를 제외한 평가 입력 |
| `trials/<id>/` | 작업 결과, 요청/응답, 프로세스·검사·호출 로그 |
| `judgments.json`, `judges/` | 동일 평가 모델의 반복 평가와 원본 로그 |
| `proposals/` | 관찰된 결과와 연결한 규칙 변경 가설 |

1. 실패한 과제와 평가 항목의 **실제 결과물·근거**를 읽습니다. 관련 규칙 경로는 원인
   후보이며, 인과관계를 증명한 것은 아닙니다.
2. 원인을 좁혀 `hypothesis`, `rule_paths`, `case_ids`, `expected_change`를 가진 짧은
   JSON을 작성하고 `bench proposal RUN --input FILE`로 저장합니다. 해당 과제 점수와
   회귀 근거, 소스·평가 기준 해시가 함께 고정됩니다.
3. 범위가 분명한 변경을 구현합니다. 점수를 올리기 위해 검사·가중치·완료 기준을 완화하거나
   과제의 정답을 일반 규칙에 넣지 않습니다.
4. 같은 기준 커밋·모델·과제로 새 디렉터리에서 세 대상을 모두 재실행합니다.
   조정용 과제와 재검증용 과제를 모두 통과해야 합니다.
5. 현재 코드에 대해 `bench gate`를 실행합니다. 코드·규칙·스킬·평가 기준·검사·초기 파일이
   측정 후 바뀌면 이전 결과를 재사용할 수 없습니다. 병합·배포는 별도의 허용 범위를 따릅니다.

품질 게이트를 확인한 릴리스/승격 절차에서 `bench gate`의 종료 코드를 사용합니다.
기본 CI는 단위·시뮬레이션 테스트만 실행합니다. 모델 인증·비용을 요구하는 실측은 자동 CI에
숨겨 넣지 않으며, 단위 테스트 성공을 실제 품질 검증 완료로 표시하지 않습니다.

## 과제와 평가 확장

기본 과제는 저장/재조회, 입력 오류와 데이터 보존, 소스 설명, 실행 가능한 문서 예제,
작은 수정, 폴더 이동과 지식 최신화를 다룹니다. `calibration`은 원인 분석에,
`holdout`은 변경의 다른 영향 확인에 씁니다. 둘 다 공개된 예제이므로 진정한 비공개
검증 세트를 대신하지 않습니다. 실제 작업의 대표 과제와 별도 보관한 과제를 추가하세요.

각 과제는 초기 파일 경로, 작업 폴더, 순차 요청, 선언한 결과물, 변경 금지 파일,
외부 Python 검사, 가중 평가 항목을 갖습니다. `before`는 후속 요청 전 외부 변경을
재현합니다. `context`는 평가자가 사실 확인에 사용할 초기 소스 경로이며, 해당 소스와
후속 외부 변경도 평가 입력에 넣습니다. 검사 프로그램은 작업 디렉터리·응답 JSON·과제 ID를 인수로 받아 다음
형태로 모든 `check` 항목을 정확히 한 번 출력합니다.

```json
{"criterion_id": {"passed": true, "evidence": "관찰한 동작과 기대 결과"}}
```

평가자는 `packet.json`의 요청·응답·선언 소스·전체 선언 결과물만 받습니다. 각 `rubric`에는
0~4점의 구체적인 기준 다섯 개가 필요합니다. 함수 정확성만 자동 검사하는 과제도
추가 사용자 요구의 유무는 평가합니다. 사람의 평가 JSON도 `report/gate --judgments FILE`로
입력할 수 있습니다. 실행의 `manifest_hash`, 고정 평가자 `{provider, model}` 식별자,
`repeats` 2~5, 표본별 `packet_hash`와 `reviews`가 필요합니다. 각 review는
`ratings: [{id, score, evidence}]`, `extra_user_requests`, `intervention_evidence`를 갖습니다.

평가 코드는 에이전트에게 전달하지 않고 종료 후 별도 복사본에서 실행합니다. 다만 이는
**협력적인 로컬 평가**이며, 악의적인 코드에 대한 OS 격리나 완벽한 익명화는 아닙니다.
답변 문체로 대상을 추측할 수 있고, 글로벌 지침·훅·모델 자체의 변동도 남습니다. 하네스를
자동 실행하는 전역 설정이 없는 전용 프로필을 사용하고, 실험 조건을 고정하세요.
자격 증명과 전역 설정은 수정하지 않습니다. 지식베이스와 작업 파일만 실행마다 분리합니다.

Codex의 보고 토큰과 Claude의 세션 누적 비용 추정치를 보존합니다. 재개한 Claude 비용을
중복 합산하지 않으며, 알 수 없는 값은 `null`입니다. 공급자 내부 작업의 완전한 사용량이나
두 공급자를 합친 실제 청구액을 추정해 채우지 않습니다. 실행 한도는 관리하는 CLI 호출에
적용하며, 독립 프로세스를 고의로 남기는 코드까지 격리하는 장치는 아닙니다.
