# 목표 계약과 질문 정책

계약은 에이전트가 조사·대화 결과로 작성합니다. 사용자가 형식을 배우거나 수동으로 채우는
문서가 아닙니다. `.loop/templates/contract.example.json`은 형식 예시이며, 실제 사용자의
답변·위임 기록이나 이미 구현된 기능을 뜻하지 않습니다.

## 목표 작성

| 필드 | 의미 |
| --- | --- |
| `version`, `id`, `title` | 형식 버전 1, 안전한 목표 식별자, 목표 이름 |
| `target.outcome` | 현재 코드와 무관한 달성 결과 |
| `target.users` | 기능을 사용할 주체 |
| `target.in_scope`, `out_of_scope` | 구현 범위와 명시적 제외 |
| `target.requirements` | `id`, `description`으로 정의한 전체 요구사항 |
| `target.acceptance` | `id`, `requirement_ids`, `scenario`, `check_ids`로 정의한 관찰 가능한 성공 기준 |
| `decisions` | 필요한 결정과 근거; 아래 10개 영역을 한 번씩 포함 |
| `open_questions` | 미해결 질문; 시작 전 반드시 빈 배열 |
| `rules` | 기준으로 적용할 저장소 상대 경로의 규칙 파일 |
| `checks` | 실제 검증 명령과 실행 위치·한도 |
| `milestones` | 순서대로 완성할 작업과 대응 인수 조건 |
| `execution` | 구현 도구와 실행 한도 |

목표·요구사항·인수 조건·검증·작업의 식별자는 중복될 수 없습니다. 모든 요구사항에는
인수 조건이, 모든 인수 조건에는 실행 가능한 검증 명령과 작업이 있어야 합니다.
마일스톤은 JSON 배열 순서대로 수행합니다. 한 인수 조건을 여러 작업에서 다시 검증할 수 있습니다.

`out_of_scope`도 명시합니다. 적용하지 않는 사항은 이유를 적으며, 모르는 사항을 `N/A`로
숨기지 않습니다. 스키마 검사는 의미의 타당성을 보장하지 않으므로 상대 도구의 사전 검토가
불필요한 질문·부족한 결정·형식적인 검증 명령까지 검토합니다.

## 시작 전에 확정할 결정

| 영역 | 조사·확정할 내용 |
| --- | --- |
| scope | 반드시 동작할 기능·사용자·제외 범위 |
| architecture | 기존 구조와 연결 방식, 변경할 경계 |
| data | 데이터 원천·저장·이관·호환성·실패 시 보존 |
| interface | UI 동작, API/CLI 입출력, 오류 동작 |
| dependencies | 외부 서비스·라이브러리·자격 증명·준비 상태 |
| security | 인증·인가·민감정보·허용 작업 범위 |
| verification | 실제 기능·통합·회귀 검증 방법과 명령 |
| operations | 실행 환경·설정·운영·관찰·실패 복구 |
| delivery | 검증된 작업 트리·커밋·PR·배포 등 도달 지점 |
| autonomy | 위임한 세부 결정, 장애 시 대안과 중단 조건 |

각 항목은 `area`, `answer`, `basis`, `rationale`을 갖습니다.
`basis`는 사용자 결정 `user`, 저장소 규칙 `repository-rule`, 기존 위임 내 판단 `delegated` 중 하나입니다.
사용자가 말하지 않은 내용을 `user`로 기록하지 않습니다. 구체적인 값이 규칙에서 나온 경우
`rationale`에 그 파일과 해당 근거를 적습니다.

## 질문을 줄이는 기준

질문 전에 코드·테스트·문서·규칙·공식 기술 자료에서 답을 찾습니다. 사용자의 기존 지시나
위임 범위로 결정할 수 있는 사항은 근거와 함께 결정합니다. 사용자 질문은 목표나 업무 규칙,
허용된 작업 범위처럼 답에 따라 제품이 달라지고 에이전트가 알아낼 수 없는 사항에 집중합니다.

예를 들어 “저장 코드는 어디에 있나요?”는 에이전트가 조사합니다. “삭제 후 복구를 제공해야
하나요?”는 목표에 없고 기존 업무 규칙으로 정해지지 않았다면 시작 전에 묻습니다.
사용자 답변이 또 다른 핵심 결정을 드러내면 시작 전 단계에서 추가 구체화합니다.

## 검증 명령

`checks` 항목은 `id`, `kind`, `argv`, `cwd`, `timeout_seconds`를 가집니다.

- `kind`: `acceptance` 또는 `regression`.
- `argv`: 문자열 배열. 셸 문자열로 해석하지 않습니다. 파이프·치환이 필요하면 저장소의
  명시적인 검증 스크립트를 호출합니다.
- `cwd`: 저장소 안의 상대 경로. 저장소 밖을 가리키는 경로·심볼릭 링크는 거절합니다.
- `timeout_seconds`: 1~3600초.

각 체크포인트에서는 해당 작업의 인수 검증과 **모든 회귀 검증**을 실행합니다.
최종 게이트는 모든 명령을 다시 실행합니다. `echo`, 빈 테스트 탐색, 무조건 성공하는 명령,
파일 존재 확인만으로 기능의 성공을 증명하지 않습니다. 테스트가 실제로 실행되는 명령을
선택하고, 검토자가 테스트의 의미와 약화 여부도 확인합니다.

검증 과정에서 생성되는 캐시·빌드 출력은 Git에서 제외된 경로에 씁니다. 검증 명령이
소스·명세 등 스냅샷 대상 파일을 수정하면 검증 결과를 무효로 처리합니다.
실제 테스트 코드와 중요한 인수 데이터는 제외하지 않습니다.

## 실행 설정

```json
{
  "orchestrator": "codex",
  "implementer": "codex",
  "max_worker_calls": 40,
  "worker_timeout_seconds": 600,
  "max_gate_attempts": 3,
  "review_timeout_seconds": 600,
  "max_run_seconds": 14400
}
```

`orchestrator`는 현재 대화 환경이며 세션 소유자입니다. `implementer`는 실제 구현을 위임받는
작업 도구입니다. 검토자는 구현 도구의 반대 공급자입니다. 생략된 `orchestrator`는 기존 계약과의
호환을 위해 `implementer`와 같게 해석합니다. 작업 도구의 호출 한도는 기본 40회, 각 위임 ID의
시도는 최대 3회입니다. ID를 새로 만들어도 전체 호출 한도는 초기화되지 않습니다.
모델은 각 CLI의 기존 설정을 사용합니다. 실행 한도도 사전 계약의 일부이며 실행 중 바꿀 수 없습니다.
작업별·최종 게이트별 시도 횟수를 각각 기록하고 재개해도 초기화하지 않습니다.
전체 시간은 `start` 이후 경과한 시간이며 중단 시간도 포함합니다.

## 진단과 실행 메모

`discovery.json`에는 현재 Git HEAD(초기 커밋 전에는 `UNBORN`), 근거가 있는 `findings`,
요구사항별 `gaps`를 기록합니다. 각 gap은 `requirement_id`, `current_state`, `work_needed`를 가집니다.
사전 진단은 고정하고, 실행 중 새로 발견한 사실은 `note`로 누적합니다.

“기존 서버가 없으므로 화면만 구현”처럼 목표를 낮추지 않습니다. 서버까지 필요한 목표라면
부족한 서버를 구현 작업에 포함하거나, 실제 외부 제약이 있다면 시작 전에 범위를 명확히 합니다.
